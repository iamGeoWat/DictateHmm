# MVP 执行计划

本文档是文档合集里唯一的"做什么"文档。其它文档是"选什么/为什么"。

## MVP 目标

**单一问题："闭嘴哼哼 + 上下文"能否在现实中被理解到可用程度？**

一切技术决策都服务于这个问题的最快验证，不做产品化工作。

## 成功/失败判定

见 [`overview.md`](./overview.md) 的"成功标准"。达不到三条之一 → 停工复盘。

## 阶段划分

### 阶段 0：可行性闪电验证（1–2 天）

只做旁路，证明"多模态 LLM 能不能听懂哼哼"。

**产出：**
- 最简 HTML 页面：麦克风录音 → 送 Gemini 2.5 Flash / Qwen3-Omni → 展示候选。
- 30 条自录哼哼 + 目标文本数据集。
- 一页实验报告：Top-5 命中率 + few-shot/上下文消融结果。

**判定：**
- 若某一模型 Top-5 命中率 ≥ 60%，进阶段 1，并保留旁路为 fallback。
- 若最好也 < 30%，直接退回"产品不成立"，或考虑纯声调链路重做。
- 30–60% 之间：继续阶段 1，同时提示成功标准需要下调或重新定义。

### 阶段 1：自建链路端到端跑通（3–5 天）

实现环节 1–7 的最简版本。**每个环节用最粗糙能跑的方案，先端到端打通。**

**任务清单：**

- [ ] 项目脚手架：Vite + TypeScript + React（或原生 DOM，UI 最小）。
- [ ] 环节 1：`getUserMedia` + AudioWorklet，16 kHz mono PCM 流，按下录音松开结束。
- [ ] 环节 2：`pitchy` 逐帧 F0，中值滤波，log + z-score 归一。
- [ ] 环节 3：能量阈值 + ≥150 ms 静音切分。
- [ ] 环节 4：规则声调分类，输出 Top-2 + 置信度。
- [ ] 环节 5：算 duration / gap / energy，只用 gap 做分词先验。
- [ ] 环节 6：离线脚本用 jieba + python-pinyin 在 10M 字语料上建"声调序列 → 词候选"索引，打包成 JSON 送到前端。
- [ ] 环节 7：前端 beam search（beam=50），KenLM trigram（WASM）打分，取 Top-20。
- [ ] LLM rerank（可选）：Top-20 + 上下文送 Claude API，取 Top-5。
- [ ] UI：麦克风按钮 + 输入框 + 候选列表 + debug 面板（F0 曲线、分段、声调序列）。

**不做：**
- 用户账号、设置、历史记录。
- 样式美化。
- 多平台适配（只要 Chrome 桌面版跑得动）。
- 任何需要大数据/训练的组件（例如 CNN 声调分类）。

### 阶段 2：评测与迭代（3–5 天）

**评测集：**
- 自建：3–5 位志愿者，每人录 30 条哼哼 + 标注目标文本 + 上下文。约 100–150 条。
- 覆盖：2–6 字常见短语、含轻声短语、含同调冲突（如全四声）。

**指标：**
- 端到端 Top-5 命中率。
- 各环节独立指标（见 [`architecture.md`](./architecture.md) "评测与回归"）。

**迭代优先级（按 ROI 估计）：**

1. 声调分类规则（阈值调整、Top-2 兜底）—— 便宜，立竿见影。
2. 候选索引语料规模（10M → 100M 字）—— 覆盖率直接提升。
3. LLM rerank 的 prompt 优化（加带调拼音、加上下文示例）—— 质量关键。
4. 分段（若经常切错字数）—— 看实测，可能需要引入 VAD。

**阶段门：** 端到端 Top-5 命中率 ≥ 60% 进阶段 3，否则重新评估。

### 阶段 3：真实用户试用（1 周）

- 找 3+ 人用 10 分钟，尝试用 DictateHmm 给朋友发一条消息。
- 记录：能否完成、用时、错误次数、主观感受（好玩？累？实用？）。
- 不要自己试，自我验证没意义。

**判定：**
- 有至少 1 人独立完成一条"有用的"消息 → MVP 成功。
- 全员都放弃 → MVP 失败，复盘原因（物理不行？学习曲线太陡？延迟？准确率？）。

## 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 哼哼本身信息量不够，任何算法都做不到 60% | 中 | 致命 | 阶段 0 旁路快速证伪/证实 |
| 规则声调分类准确率上不去（<70%） | 中 | 高 | 用 Top-2 兜底到候选层；或提前上 CNN |
| 候选索引太大/太慢 | 低 | 中 | 先词级，再字级；分片加载 |
| LLM rerank 成本/延迟超预算 | 中 | 中 | 减少 rerank 频率，只在 commit 时做 |
| 用户不愿意停顿 150 ms | 高 | 中 | 加"节拍模式"兜底 |
| 浏览器麦克风/AudioWorklet 坑 | 中 | 低 | Chrome 桌面优先，其它后置 |

## 不在 MVP 范围

- 任何"本地离线"能力（本地 LLM 可以阶段 3 后研究）。
- 移动端（手机浏览器可能跑得动但不优化）。
- 输入法系统集成（iOS Keyboard Extension / Android IME）。
- 用户个性化 / 账号 / 同步。
- 多语言（粤语、方言）。
