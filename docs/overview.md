# 项目总览

## 问题描述

中文有声调，四个基本调（加轻声五类）本身就携带了可观的信息量。中国人在日常对话中，如果懒得张嘴，闭嘴哼几声（"哼哼哼"），对方往往能结合上下文听懂——例如"哼（4）哼（3）哼（1）"能被解读为"汉堡包"。

**目标：** 做一个输入法，用户只用"哼"（不发元音、不做唇形）产生候选中文，结合上下文给出最可能的候选词/句。

**核心假设：**
- 哼哼里只稳定传递**声调**和**节奏**信息，几乎丢失了声母/韵母。
- 声调 + 节奏 + 上下文，信息量足以让用户从候选里快速选中目标。
- 因此本质是：一个把"声调序列（+节奏）+ 上下文"映射到"中文候选序列"的输入法。

## 与相关问题的区别

| 相关领域 | 关键差异 |
|---|---|
| ASR（语音识别） | 我们**没有**声母/韵母信息，ASR 模型会失败 |
| Query-by-Humming（音乐检索） | 目标是检索旋律，不做离散声调解读 |
| 普通拼音输入法 | 输入是 <声母+韵母+声调> 三元组；我们只有声调 |
| 耳语（whisper）识别 | 耳语仍保留共振峰；哼哼基本没有 |

因此不能直接套用现成系统，需要专门建模。

## 信息量粗算

- 普通话有约 **400** 个有调音节，**~1300** 个含调音节（加声调）。
- 仅声调：4~5 类。一个 n 字词的声调序列空间只有 `5^n`，远小于拼音输入法的 `1300^n`。
- 举例：4 字词声调序列空间 ≈ 625；而 4 字拼音空间 ≈ 2.86×10¹²。
- 因此**必须**强依赖上下文与词频先验，才能把候选收敛到可用。

## 术语

- **F0 / 基频**：音频信号的基本周期对应的频率，感知为"音高"。
- **声调（tone）**：普通话四声（1=高平、2=升、3=降升、4=降）加轻声。
- **Pitch contour**：一段时间内 F0 的变化曲线。
- **VAD**：Voice Activity Detection，检测有无语音活动。
- **Onset**：声音的起始点。
- **分段 / segmentation**：把连续音频切成单个音节的过程。
- **Lattice**：解码时所有可能候选序列构成的图。
- **N-gram LM**：基于 n 元词组频率的语言模型。

## 总体思路

把问题拆成可独立验证、可独立替换的流水线（见 [`architecture.md`](./architecture.md)）：

```
音频 → F0 提取 → 分段 → 声调分类 →（节奏特征）→ 候选生成与排序 → 候选列表
```

旁路："直接把音频+上下文扔给多模态 LLM"（见 [`stages/bypass-multimodal.md`](./stages/bypass-multimodal.md)）——作为懒人方案或 fallback。

## 成功标准

**MVP 成功 = 以下三条同时成立：**

1. 在安静环境下哼 3–5 字常见短语，目标结果出现在 Top-5 候选内的概率 ≥ 60%。
2. 从按下麦克风到出候选的端到端延迟 ≤ 1 秒。
3. 三位以上真实用户在 10 分钟训练后，能用它完成至少一条"有用"的消息（如发给朋友的短句）。

达不到这三条就不做产品化。

## 非目标（MVP 阶段）

- 超过 6 字的长句。
- 噪音环境（街头、地铁）。
- 多语言/方言。
- 跨设备输入法系统集成（iOS/Android IME API、输入法框架）。
- 本地离线运行（MVP 可以用云端 LLM）。
