# 旁路：多模态 LLM 直接音频 → 文字

## 问题定义

绕过整个流水线，直接把哼哼音频片段 + 上下文喂给多模态 LLM，让它输出候选中文。

**适用场景：**
- MVP 验证期：几天出 demo，验证"哼哼能否被理解"这件事本身。
- 产品化的 fallback：本地链路低置信度时走云端多模态。
- 高精度场景：用户愿意等 1–2 秒换最高质量。

## 可用模型（2026）

| 模型 | 音频支持 | 首 token 延迟 | 价格（粗略） | 部署 |
|---|---|---|---|---|
| **Gemini 2.5 Flash** | 原生音频 in；Live API 流式 | 300–800 ms / < 200 ms (Live) | ~$0.30 / $2.50 per M tokens | 云端 API |
| **Gemini 2.5 Pro** | 原生音频 in | 800 ms–2 s | ~$1.25 / $10 per M | 云端 API |
| **GPT-4o audio** (`gpt-4o-audio-preview`) | 异步音频 in/out | 500 ms–1.5 s | ~$2.50 / $10 per M | 云端 API |
| **GPT-realtime** | WebSocket 流式 | 300–500 ms | 音频 token 溢价 | 云端 API |
| **Claude (audio blocks)** | 部分部署支持 | — | — | 云端 API |
| **Qwen2.5-Omni / Qwen3-Omni 7B** | 本地可跑 | 200–400 ms (4090) | 免费（权重） | HF / 本地 GPU |

## Prompt 设计

```
System:
你是一个中文输入法后端。用户无法说话，只能闭嘴哼
（仅传递声调和节奏，没有声母韵母信息）。
你将收到：
1. 用户刚才哼的一段音频。
2. 最近 N 条聊天上下文。
任务：输出 5 个最可能的候选中文短语，按可能性排序，
用 JSON 数组返回：{"candidates": ["...", "...", ...]}
不要解释，只返回 JSON。

User:
上下文：朋友刚问："晚饭吃什么？"
[audio: 用户的哼哼]
```

### 经验要点

- **明确告知模型哼哼的特性**（无声韵母，仅声调/节奏）——不说的话模型会按 ASR 思路尝试识别元音，结果乱套。
- **给带调拼音作为中间表示**：要求模型先输出带调拼音 + 再给汉字，能显著提升稳定性（chain-of-thought 式）。
- **严格 JSON 输出**：用 structured output / JSON mode，前端直接解析。
- **每次请求带上下文**：上下文是歧义消解的核心，没有上下文直接输出候选质量显著下降。

## 可行性风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 模型没见过"仅哼声调" | 训练数据里几乎没有，可能表现不稳定 | Few-shot：prompt 里给 2–3 个示例哼音频 + 标注 |
| 声调识别错误 | 模型的音频 encoder 未必精细到四声 | 比较不同模型，Gemini/Qwen-Omni 在中文音频上可能更强 |
| 延迟 | 1–2 s 的端到端延迟在输入法场景偏慢 | 只在低置信度时走旁路；或者用 Live API |
| 成本 | 每次输入一次 API 调用，按秒计费 | 本地链路先过滤明显候选，只把难的给云端 |
| 隐私 | 用户声音上云 | 产品化需做本地 inference 或显式同意 |

## 实验设计

做旁路验证时，先固定以下 3 个问题：

1. **单模型能否听懂"哼哼"**：自己录 30 条哼哼（带已知目标），Gemini 2.5 Flash 和 Qwen3-Omni 分别跑，对比 Top-5 命中率。
2. **Few-shot 提升多少**：同样样本，prompt 里放 0 / 2 / 5 个示例，看命中率曲线。
3. **上下文提升多少**：同样样本，给 0 / 最近 1 条 / 最近 5 条上下文，看命中率曲线。

这三点清楚之后，再决定旁路是作为"唯一方案"还是"fallback"。

## MVP 建议

**平行实现两条链路：**

1. **链路 A（主）**：流水线 1–7 环节，用规则 + 词典 + 云端 LLM rerank。
2. **链路 B（旁路）**：直接 Gemini 2.5 Flash（或 Qwen3-Omni）音频直出。

UI 上同时展示两路候选，让用户选，顺便收集"哪条更准"的数据。一周后根据数据决定主力路线。

## 开放问题

- 多模态 LLM 对"非语音音色"（哼、吹口哨）的鲁棒性未知——即使是 2026 的模型。
- 是否能通过**在 prompt 里直接描述声调序列**（"四声—三声—一声"）代替音频输入？这样就能把环节 4 的输出喂 LLM，不用传音频，便宜且快。实测值得做。
- 旁路是否可以"微调"？Gemini/Qwen 允许 fine-tune 时，用几百条哼哼-汉字对微调效果如何？
