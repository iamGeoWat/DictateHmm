# 环节 3：分段

## 问题定义

**输入：** PCM + F0 序列。
**输出：** `Array<{startMs, endMs}>`，每个元素对应用户哼的一个"音节"（预期一字一段）。
**要求：**
- 漏检率低（漏一段就漏一个字）。
- 过切率低（把一个连贯的哼切成两半，会多出候选字）。
- 实时：收到一帧就能决定是否更新当前段。

## 关键观察：哼哼没有辅音 onset

普通语音的 onset 检测依赖辅音爆破/摩擦的宽频能量突变。哼哼是纯浊音、纯基频，**频谱几乎恒定**，传统 onset 算法（spectral flux、HFC）**失效**。

可用信号：
1. **能量包络**（RMS）：用户在字与字之间会有短暂能量下降甚至静音。
2. **F0 稳定性**：单个字内 F0 曲线连续，段之间会有 F0 重置（unvoiced gap 或跳变）。
3. **用户行为约束**：MVP 直接要求用户在字间有 ≥ 150 ms 停顿。

## 方案对比

| 方案 | 精度 | 延迟 | 依赖用户配合 | 备注 |
|---|---|---|---|---|
| **能量阈值 + 最小静音 ≥ 150 ms** | 中 | ~1 frame | 强 | MVP 首选，≤ 50 LOC |
| Silero VAD (`@ricky0123/vad-web`) | 高 | ~10 ms | 弱 | 1–2 MB ONNX，跑浏览器 |
| WebRTC VAD | 低 | < 1 ms | 强 | 对非"speech-like"声音（哼）判断不稳 |
| TEN-VAD | 高 | ~10 ms | 弱 | 2025 新 VAD，低误报 |
| essentia.js Onset (HFC/flux) | 低（本场景） | 中 | — | 哼哼没有 onset，可能完全失灵 |
| meyda 手写 spectral flux 阈值 | 低 | < 1 ms | — | 同上 |
| F0 断点检测（pitch stability window） | 中 | 中 | 中 | 段内 F0 差分小，段间大 |
| 用户手动断词（按键/点击/敲桌子） | 最高 | 0 | 最强 | 兜底方案 |
| 端到端神经分段（自己训） | 高 | — | 无 | 需要哼哼标注数据，暂无 |

### Silero VAD 注意

Silero 是为"说话 vs 非说话"训练的，哼哼可能被判为"非说话"。实测前先跑几段哼哼，看它能否把哼分段。如果不行，需要结合能量阈值。

## MVP 选型

**两级方案：**

1. **主路径：能量阈值 + F0 稳定性**
   - 归一化 RMS 后设阈值（例如 -35 dBFS）。
   - 低于阈值且持续 ≥ 150 ms 视为段间隔。
   - 段内若 F0 gap（连续 unvoiced 帧）> 80 ms，也切一刀。
   - 段太短（< 60 ms）丢弃。

2. **兜底：用户可切换"节拍模式"**——按空格/点击标记每字边界，完全消除分段错误。适合重要场景（密码、数字）或噪声环境。

不用 Silero 是因为：MVP 安静场景 + 用户主动配合停顿，能量阈值就够；并且 Silero 对哼的行为未经验证，先不引入复杂依赖。

## 升级路径

1. **嘈杂环境** → 能量阈值改用相对阈值（背景噪声 baseline + Δ），或引入 Silero/TEN-VAD。
2. **连哼无停顿场景** → 训一个专用的"哼哼分段"小模型（F0 + 能量的 1D CNN），需要数据。
3. **节奏输入**（想用节奏编码词边界）→ 保留段间 gap 时长供候选匹配使用。

## 评测

标注集：找 5 人各录 20 段哼（2–6 字），人工标 start/end。
指标：
- **段边界 IoU ≥ 0.8** 的比例。
- **字数正确率**：分段出的段数 == 目标字数 的比例（这个指标比 IoU 更贴近用户体验）。
- **延迟**：从最后一帧音频到分段完成。

## 开放问题

- 哼哼时用户会不会下意识连成"哼—嗯—哼"（省去换气），分段会完全错。需要真实用户数据验证。
- 150 ms 停顿是否太不自然，把速度拖到不可用？可能需要动态调整：哼得快时阈值放松。
- 边哼边出候选（streaming）下，段还没结束就开始做声调判定，是否能接受？
