# 系统架构

## 流水线总览

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ 1. 音频采集   │──▶│ 2. F0 提取    │──▶│ 3. 分段       │──▶│ 4. 声调分类   │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
                                                                  │
                          ┌──── 5. 节奏特征（并行） ─────────────┘
                          ▼
                   ┌──────────────┐      ┌──────────────┐
                   │ 6. 候选生成   │─────▶│ 7. 候选排序   │────▶ 候选列表
                   │  与剪枝      │      │ （LM / LLM）  │
                   └──────────────┘      └──────────────┘

             旁路：
             ┌─────────────────────────────────────────┐
             │  音频 + 上下文 ──▶ 多模态 LLM ──▶ 候选   │
             └─────────────────────────────────────────┘
```

## 环节职责

| # | 环节 | 输入 | 输出 | 可独立测试？ |
|---|---|---|---|---|
| 1 | 音频采集 | 麦克风 | PCM 流（16 kHz mono） | ✅ 听回放 |
| 2 | F0 提取 | PCM 流 | `Array<{time, f0Hz, voiced, confidence}>` | ✅ 画曲线 |
| 3 | 分段 | F0 + 能量 | `Array<{startMs, endMs}>` | ✅ 叠在波形上看 |
| 4 | 声调分类 | 每段的 F0 子序列 | `Array<1\|2\|3\|4\|5>` + 置信度 | ✅ 与自报对比 |
| 5 | 节奏特征 | 分段结果 | `{duration[], gaps[], energyPeaks[]}` | ✅ 打印 |
| 6 | 候选生成 | 声调序列 + 节奏 | Top-K 中文序列（未排序/粗排） | ✅ 字典查询即可 |
| 7 | 候选排序 | Top-K + 上下文 | 最终候选列表 | ✅ 评测集 |

可独立测试是关键——每环节都能肉眼或脚本验证对错，定位 bug 不用端到端猜。

## 数据接口定义

统一用 TS 类型约束各环节边界。放在将来的 `src/types.ts`：

```ts
// 单帧 pitch 样本
type PitchFrame = {
  timeMs: number;    // 相对段开始
  f0Hz: number | null; // null 表示 unvoiced
  confidence: number; // 0-1
};

// 一段哼（一个音节）
type Segment = {
  startMs: number;
  endMs: number;
  pitch: PitchFrame[];    // 本段内的 F0 曲线
  energyPeakDb?: number;
};

// 声调判定
type ToneLabel = 1 | 2 | 3 | 4 | 5; // 5 = 轻声
type TonedSegment = Segment & {
  tone: ToneLabel;
  toneConfidence: number;
  altTones?: Array<{ tone: ToneLabel; confidence: number }>;
};

// 候选
type Candidate = {
  text: string;       // 汉字序列
  pinyin: string[];   // 带调拼音（可选）
  score: number;      // 排序得分
  source: 'dict' | 'lm' | 'llm' | 'multimodal';
};
```

## 组件边界

MVP 阶段所有组件都在浏览器内运行（可选：候选排序走云端 LLM API）：

```
Browser:
  - AudioWorklet  (#1)
  - WASM / JS     (#2, #3, #4, #5)
  - JS + WASM     (#6: dict + KenLM)
  - WebGPU LLM    (#7 local) 或 Fetch → LLM API (#7 云端)
```

## 失败与降级策略

每个环节都应该能"低置信度通过"而不是硬失败：

- F0 提取：unvoiced 帧标记 `null`，下游自行决定是否丢弃。
- 分段：若检测不到明显边界，返回整段作为单段，让用户手动断词。
- 声调分类：输出 Top-2 候选 + 置信度，不强行选一个。
- 候选生成：如果词典查不到，退化为字符级候选。
- 候选排序：LLM 失败时退回本地 n-gram LM。

全链路降级到极端：分段+声调都失败时，把原始音频直接扔给旁路多模态 LLM。

## 评测与回归

每个环节独立评测集：

- F0：合成/人工标注的正弦扫频 + 真人哼，误差阈值 < 5%。
- 分段：人工标注的 start/end，IoU > 0.8。
- 声调：人工标注的 4 声 isolated 样本，分类准确率。
- 候选：人工标注的 `(声调序列 + 上下文) → 目标文本` 数据集，Top-K 命中率。

端到端评测：真实对话场景里的 Top-5 命中率 + 延迟。

评测集放 `eval/` 目录（未建），每次改动相关环节先跑对应评测。

## 未定的设计决策

这些会在动工过程中拍板，先记在这里：

1. **Streaming vs. Batch**：MVP 是按下麦克风说完松开出结果（batch），还是边哼边出候选（streaming）？倾向 batch，但需评估用户体验。
2. **手动断词**：是否强制用户在哼哼间隔 > 150 ms，作为分段硬约束？MVP 倾向是。
3. **上下文窗口**：排序时用多少 tokens 的聊天历史作为上下文？
4. **本地 vs 云端**：MVP 用云端 LLM（简单、强），产品化后回到本地 Qwen 0.5B。
